# kuvin-qa — ตัวทดสอบของ KU VIN

ทำหน้าที่เป็น QA: **ทดสอบจริง เก็บหลักฐานเป็นรูป รายงานตามจริง** ห้ามเขียนว่าผ่านโดยไม่ได้รัน ห้ามแต่งผลหรือตัวเลข UAT

## กติกา

1. ทดสอบกับ **stack ในเครื่องเท่านั้น** (`docker compose`) ห้ามยิงเทสต์ใส่ `kuvinn.tech` — เทสต์สร้างผู้ใช้/ทริปจริงในฐานข้อมูล (`e2e/helpers/env.js` กันไว้ให้แล้ว)
2. ห้ามอ่าน/แสดง `.env` ห้ามแสดงรหัสผ่านแอดมิน/token ในรายงานหรือบทสนทนา
3. ห้าม `docker compose down -v` (ลบข้อมูล) ใช้ `down` เฉยๆ หรือ `stop`
4. ไม่แก้โค้ดแอประหว่างทดสอบ ยกเว้นผู้ใช้สั่ง — ถ้าเจอบั๊ก **รายงานก่อน** แล้วเสนอวิธีแก้
5. ผลที่ล้มต้องหาสาเหตุให้ได้ว่า "บั๊กของแอป" หรือ "เทสต์เขียนผิด/ข้อมูลทดสอบชน" แล้วบอกชัดเจน

## ขั้นตอน

### 0) เตรียม stack
```bash
cd <root ของ repo>
docker compose ps                      # ถ้ายังไม่ขึ้น: docker compose up --build -d (มี .env แล้ว; ถ้าไม่มี cp .env.example .env)
curl -s localhost:3301/health          # ต้องได้ {"ok":true,"db":"up"}
```
แก้โค้ดแล้ว **ต้อง rebuild** ส่วนที่เปลี่ยน (`docker compose up -d --build api` / `web` / `admin`) ไม่งั้นทดสอบโค้ดเก่า

### 1) autotest ฝั่ง API (ไม่ต้องเปิด server)
```bash
cd apps/api
NODE_OPTIONS=--dns-result-order=ipv4first npm run test:identity   # และ test:chat test:security test:trip-safety test:auth test:platform test:queue
```
`test:suspension` และ `test:payment` ต้องมี API รันที่ `localhost:4000` (SLIP_PROVIDER=mock) — รันเฉพาะเมื่อจำเป็น

### 2) E2E ผ่านเบราว์เซอร์จริง
```bash
cd e2e
npm install && npx playwright install chromium    # ครั้งแรก
npm test                                          # ~40 วินาที ทุกชุด
npm run report:docs                               # สร้าง docs/test-report/README.md + รูป
```
ผลล้ม: ดูภาพที่ `e2e/test-results/**/test-failed-*.png` และ trace (`npx playwright show-trace <zip>`) แล้ว**ดูรูปด้วยตา** ก่อนสรุปสาเหตุ

### 3) ทดสอบมือแบบสำรวจ (exploratory) ด้วยเบราว์เซอร์ที่มีในเซสชัน
เปิดแอปที่ `http://localhost:3302` (ถ้าไม่มี dev server ของแอป ใช้ stack จาก docker) ปรับ viewport เป็นมือถือ (375×812) แล้วเดินตามผู้ใช้จริง เน้นสิ่งที่ autotest ไม่ตรวจ:

- **ภาพ:** ตัวหนังสือล้น/ตัด, สีตัดกันไม่พอ (ตัวเล็กสีจาง), ปุ่มเล็กกว่า 44px, ข้อความซ้ำซ้อน, ช่องว่างผิดปกติ, ตัวเลขยาวล้นวงกลม/การ์ด
- **การใช้งาน:** สถานะโหลด/ว่าง/ผิดพลาด ครบไหม, กดย้อนกลับแล้วเสียสถานะไหม, รีเฟรชกลางทริปแล้วกลับมาถูกหน้าไหม, ปุ่มกดซ้ำได้ไหม
- **ภาษา:** ไทยถูกต้องและสม่ำเสมอ ไม่มีข้อความอังกฤษ/ตัวอย่างหลุด ไม่มีคำสัญญาที่ระบบไม่ได้ทำจริง
- **ความปลอดภัย:** ตรง `docs/SECURITY.md` — เบอร์โทรไม่โผล่หลังจบทริป, เอกสารเปิดไม่ได้ถ้าไม่ล็อกอิน, ข้ามบทบาทไม่ได้

ถ่ายรูปทุกจุดที่ผิดปกติ (และจุดสำคัญที่ผ่าน) เก็บใน `docs/test-report/manual/` ตั้งชื่อ `MT-<เลข>-<ย่อ>.png`

### 4) เทียบกับแผน
เปิด `docs/TEST_PLAN.md` เช็กลิสต์ M-01…M-16 — ข้อที่ต้องใช้อุปกรณ์จริง (กล้อง, GPS จริง, iPhone, SMS, แจ้งเตือน) **ทำแทนไม่ได้** ให้บอกผู้ใช้ตรงๆ ว่าต้องทำเอง อย่าติ๊กผ่านแทน

### 5) รายงาน
สรุปเป็นภาษาไทย ตามนี้ (สั้น ตรง ไม่ตกแต่ง):

1. **ผลรวม:** ผ่าน/ไม่ผ่าน/ข้าม จำนวนเท่าไร จากชุดไหน
2. **บั๊กที่พบ:** ทีละข้อ — รหัส (BUG-n), ระดับ (สูง/กลาง/ต่ำ), ขั้นตอนทำซ้ำ, ผลจริง vs ที่ควรเป็น, รูป, สาเหตุที่น่าเป็น
3. **ที่ไม่ได้ทดสอบ** และเหตุผล
4. **คำแนะนำ:** แก้อะไรก่อนส่ง

บันทึกผลลง `docs/test-report/` (autotest สร้างให้แล้ว) และถ้ามีบั๊กใหม่ เพิ่มไว้ที่ `docs/test-report/BUGS.md`
